# PLAN-0001 — Plan-scoped approval and engineering rules

> Status: PENDING
> Revision: 1
> Repository: iAmStarter/istartsoftflow
> Scope: workflow framework only
> Approval: REQUIRED BEFORE IMPLEMENTATION

## Goal

Keep iStartSoftFlow's single-source-of-truth methodology and vertical-slice workflow while making approvals scoped to one immutable plan revision, tightening unsafe enforcement gaps, and standardizing feature-based engineering and concise Git history.

## Findings (verified)

1. `.issflow/hooks/plan-gate.js` reads `docs/PLAN.md` and allows writes when the plan is absent, the approval line is missing, or input parsing fails.
2. It exempts the active feature lane based on `docs/STATE.md`, without independently verifying that feature's approved plan revision.
3. Its writable-path allowlist includes `.github/`, `.issflow/`, and arbitrary top-level Markdown even while a plan is pending; these can affect execution rules.
4. The current hook uses Claude-specific `PreToolUse` input. The Codex adapter explicitly describes its rituals as model-run rather than enforced.
5. Feature-based architecture and naming conventions already exist; preserve them.

## Changes proposed

### A. Plan identity and approval

- Use one plan file per task: `docs/plans/PLAN-<id>.md` (or feature-scoped `docs/features/<slug>/PLAN.md` with a unique ID).
- Each plan declares `Plan-ID`, `Revision`, `Status`, scope, changed-file boundaries, acceptance criteria, tests, and risks.
- Record human approval in a separate approval record bound to the plan's content digest, ID, and revision. A modified plan invalidates the prior approval.
- Approval must be attributable to a human action; never self-approve or infer approval from a generated file.
- Keep the legacy `docs/PLAN.md` path compatible during migration; no mass rewrite of installed projects.

### B. Enforcement

- Refactor the Claude plan gate to fail closed for source mutations when an expected approval is missing, malformed, or stale.
- Do not exempt an active feature merely because `docs/STATE.md` says `(active)`.
- Restrict modifications to policy files, hooks, CI workflows, and approval records while approval is pending; allow safe planning documents.
- Explicitly document limitations of model-only enforcement in Codex. Add a deterministic local/CI verifier and a documented command to run it; do not claim Codex cloud has a native pre-edit hook without verifying support.
- Provide an emergency/manual recovery procedure for malformed metadata without silently bypassing policy.

### C. Engineering conventions

- Default to feature-based organization with small cohesive modules and clear domain boundaries.
- Keep `src/app` thin in Next.js projects; business rules belong in feature modules.
- Prefer explicit types, readable names, minimal abstractions, and comments explaining *why* rather than narrating code.
- Commit messages use short Conventional Commits, e.g. `fix(auth): validate session`.
- Do not insert tool promotional signatures or AI-attribution boilerplate into comments or commit messages. Preserve authentic Git author/committer metadata and required disclosure policies.

### D. Tests and migration

- Add Node tests for pending, approved, revised, forged/missing, feature-active, malformed, and legacy-plan cases.
- Verify shell/Bash-mediated edits and CI changes are not silently treated as protected by a Claude Edit-only hook.
- Run installer/build checks and test non-destructive installation behavior.
- Update the installer template via the project's existing build process; avoid hand-editing generated template copies.
- Update README and Thai how-to with setup, approval workflow, Codex limitations, and upgrade guidance.

## Non-goals

- No change to TwinFlow business logic or production.
- No automatic merge, release, or npm publish.
- No rewriting unrelated iStartSoftFlow methodology.
- No impersonating human commit authors.

## Acceptance criteria

1. A pending plan blocks unapproved implementation in supported enforcement paths.
2. Approval for PLAN-A revision 1 cannot authorize PLAN-B or PLAN-A revision 2.
3. A feature lane cannot bypass approval by editing STATE.md alone.
4. Invalid approval metadata fails safely with actionable errors.
5. Legacy installations have a documented migration path.
6. Test suite covers gate bypasses and installer output.
7. All code changes remain in a separate branch and a reviewable PR.

## Execution after approval

1. Implement and test approval record verification.
2. Harden supported hooks and add CLI/CI verifier.
3. Update methodology and engineering conventions.
4. Rebuild installer templates and run tests.
5. Open a review PR; never merge or publish automatically.
